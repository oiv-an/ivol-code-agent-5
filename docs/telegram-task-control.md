# Telegram task control

## Setup

1. Create a dedicated bot with BotFather and enable topics in private chats. Do not share this bot with another polling service or an active webhook.
2. Open your bot in Telegram and press **Start** so it can send you messages. IVOL does not reply in the general chat.
3. Open **Settings → IVOL → Telegram**. Enter the bot token and your numeric Telegram user ID. The linked ID helper is a third-party bot, not an IVOL service.
4. Create or open a task **in the plugin**, then press **Connect Telegram** below the chat.

The plugin creates a private topic on first activation and reuses its saved topic on later activations. New topics use a short title from the original request (no task ID). Before the work-start notice, the full original request is sent as plain text and its first message is pinned. Long requests are split without truncation. Existing topics are not renamed and their descriptions are not replayed. If initial delivery/pinning fails, activation fails visibly; reconnecting reuses the saved topic without retrying the description, avoiding duplicates. Each explicit activation sends a work-start notice. Switching to an unrelated task disconnects the previous task in that window; the next task must be activated explicitly. Other windows remain independent.

### Connection toggle

The chat button has a green background, white icon and green border only after the backend confirms an active connection for the displayed task. Its accessible pressed state follows that confirmation, not the click. Click **Disconnect Telegram** to stop mirroring; the green state clears on the backend inactive acknowledgement. Connecting and subtask handoffs show a spinner without green and remain cancellable with the same disconnect button, even during the brief gap without a focused task. The root topic identity scopes cancellation across a handoff; a stale disconnect from an unrelated task cannot stop another connection. Double clicks do not enqueue duplicate toggle requests. Remounting or switching tasks requests a fresh state instead of retaining a previous task's green indicator.

Disconnect detaches the host bridge, closes its local client and aborts the coordinator route, clearing pending output and incoming downloads. No new queued publications are started after the coordinator processes disconnect; late activation/handoff completions cannot restore the connection. A Telegram HTTP request already in flight may still be accepted remotely before cancellation arrives. Disconnect does not recall or delete already sent messages, and it does not stop the local agent itself.

### One topic for a task tree

While connected, agent-created subtasks inherit the original topic, including nested children and returns to their parents. The original activation is the root of this connection; activating a child independently does not attach its ancestors. Only the active task receives input. Child creation and parent resumption do not create another topic or repeat the root description, pin or start notice. Existing history is never replayed; new child events emitted during construction are buffered (1000 messages / 32 MiB) until the new bridge is bound. Output already accepted by the coordinator remains in the same ordered outbox. Message identities include a connection epoch so equal timestamps and thinking indicators in different tasks cannot overwrite each other.

**Input during a handoff is fail-closed, not a durable queue.** While the button shows connecting, do not send input: text, photos and `/stop` arriving in the transfer gap, and the ambiguous second immediately following it, are not executed or replayed. Resend after the active state returns. Old approval buttons are revoked; they never approve the new task's question. Downloads from the old epoch are cancelled and their late results discarded. Input received alongside the new route acknowledgement is bounded to 32 messages / 32 MiB and delivered only to that exact new epoch. If the outgoing task already has queued Telegram input, transfer disconnects visibly rather than silently assigning that input to the child; inspect the old task and resend deliberately. A handoff has a 15-second timeout on both host and coordinator. Cancellation, errors, unrelated navigation and manual deactivation invalidate it; a late response cannot reactivate Telegram. No Telegram connection is started merely because an agent delegates a task.

## Controls and mirrored content

- Send text, a photo/screenshot, or a PNG/JPEG image document in the active topic. Photos use the largest available variant. The caption and image become one ordinary task message: an answer to a pending follow-up, or queued input when the agent is busy. Images appear in the normal IDE conversation and are passed through the model's existing image-input mechanism (a vision-capable model is required). No caption is required.
- Albums are processed as separate messages in Telegram update order, not merged. Only the caption attached to each individual photo accompanies it. A caption containing `/stop` is image context, not a command; send `/stop` as a separate text message.
- Tool approvals require their current inline buttons. Ordinary text or images cannot approve tools, commands, browser launch or MCP execution.
- Terminal output buttons continue or abort the terminal operation. Retry/continue, bug-report, context-condensation and auto-approval-limit questions can continue the existing task; their reject button stops rather than creating another task. Condensation refusal never sends a plain negative response, because the underlying condensation tool treats an empty response as acceptance.
- Follow-up questions (including explicit pre-condensation decisions) and condensation feedback accept text directly. Completion/resume-completed rows accept queued feedback, not a remote "new task" action. Account/payment/model-selection dialogs and checkpoint restoration remain IDE-only: they require UI-specific actions, not a generic task approval. Checkpoint-restore confirmation rows inserted directly by the UI are not task-message events and are not mirrored.
- Approvals carry monotonic revisions, are invalidated independently of output delivery, and are consumed once. The host rechecks the exact pending task question before every action. Only a valid current owner/route callback receives `answerCallbackQuery`; acknowledgement failure is reported without retrying the action or disconnecting unrelated routes. Unknown, stale, duplicate and offline callbacks remain silent. An already in-flight Telegram request can briefly display obsolete buttons; those buttons cannot execute an obsolete action and are cleared by the queued refresh.
- Send `/stop` to cancel the current task.
- Only assistant text, completion/subtask results and follow-up question text are mirrored. Internal tool/API/reasoning/checkpoint/progress payloads and user feedback are not sent. One “Thinking…” message per active phase is replaced by the next answer; streaming updates edit that answer. Old request-metric updates do not restart the indicator.
- Assistant Markdown is parsed as CommonMark into plain text plus explicit Telegram entities: bold, italic, inline code, fenced code, safe HTTP(S)/mailto links and readable lists. Raw HTML stays literal, never executes, and unsafe link destinations are not made clickable. No Markdown/HTML parse mode is sent. Messages split at at most 4000 UTF-16 units without splitting surrogate pairs; formatting/link/code spans are clipped into valid per-message entities. Streaming edits compare both text and formatting and clear obsolete tail chunks/buttons. Malformed Markdown remains readable; parser failure or excessive entity density falls back to plain text. Original task descriptions, notices and approval summaries remain plain.
- Completion suggestions are IDE metadata, not assistant replies: structured completion asks (including their streaming prefixes) are suppressed. Normal completion results, plain completion questions and JSON/code examples in assistant answers remain visible. Suggestions are never executed.
- Pending approvals show a safe generic summary with current buttons, never tool arguments, paths or command output. Review the exact action in the IDE before approving. Outgoing inline images are accepted only from explicitly allowed assistant rows. Browser screenshots and generated local-file image JSON are not mirrored; incoming photos remain supported.
- Text and images share one ordered, bounded in-memory outbox (32 MiB / 1000 pending items per connection); image acknowledgement means accepted into that queue, not delivered to Telegram. Delivery failures deactivate the route and report an error. Disconnect discards pending output; there is no durable replay or exact-delivery guarantee.
- Incoming downloads authorize owner/topic/activation epoch before requesting any file, and recheck the epoch and heartbeat after asynchronous work. Only Telegram `getFile` and its fixed file API host are used; redirects, arbitrary URLs, traversal paths and query strings are rejected. Downloads have a total 20-second deadline, a 10 MiB binary limit checked against metadata/headers and streamed bytes, and PNG/JPEG signature validation. Errors never include the bot token, remote URL or Telegram response description.
- Incoming text/images use an ordered queue of at most 32 pending messages per route, with one download per route and at most four downloads across windows. The task-side Telegram queue is additionally bounded to 32 messages / 32 MiB of text and encoded image characters. Limits or download failures visibly disconnect that route and discard pending coordinator work; reconnect from the plugin. Polling, approvals and `/stop` do not wait behind downloads. Stop/disconnect cancels the route's downloads, and late results cannot reach another task or a reactivated epoch.
- Existing history is not automatically replayed. Hidden model reasoning, arbitrary local files, external image URLs, non-image documents, stickers/video/audio and voice messages are not supported: they are ignored, not downloaded, transcribed or passed to the model. Captions on unsupported media are not treated as standalone text. Unsupported outgoing image data produces a visible connection error rather than being silently lost.

General chat, unknown topics, inactive topics and other senders are ignored. No remote operation creates or opens an IDE task. Offline messages are not replayed. Messages in the ambiguous activation second are intentionally rejected, so wait a moment after the notice before replying.

## Local coordinator and privacy

A detached local process owns one long poller per bot, shared across local IDE windows. An authenticated local MCP connection carries plugin control requests; it is not registered as a model-visible MCP server. Credentials reach the child only through parent IPC, never command arguments or a credentials file. The plugin stores them in its extension secret-storage API. The storage implementation and protection depend on the IDE host.

The runtime directory in the user's home is `.ivol-telegram`. On Unix its mode is 0700, the socket and topic registry use 0600. Mutual HMAC authentication is required on Unix and Windows. The registry contains hashed task bindings and topic IDs, not tokens or message content. Telegram receives the mirrored conversation, which can include sensitive source code in assistant replies or the original request.

Closing the last window eventually stops the coordinator. Heartbeats expire after 15 seconds; the idle coordinator exits after 30 seconds without peers. Polling errors invalidate routes and require explicit reactivation. Sessions also require reconnection after six continuous days, before Telegram may randomize its update sequence after a week of inactivity. Failed deliveries are not automatically retried after ambiguous network failures, avoiding silent duplicates. Explicit rate-limit responses receive one bounded retry.

Activation failures appear in a visible IDE notification and webview state, with a fixed diagnostic code in the IVOL Code output channel. API responses, exception stacks, tokens and IPC credentials are never logged. Codes distinguish disabled private-chat topics, active webhook, rejected token, another poller, API availability/rate limit, and local startup failures. A generic local/startup code does not establish a bot misconfiguration; retry and inspect the notification. Installing a VSIX into an already-running IDE does not itself reload every extension host.

A renewable local lease serializes startup and stale-socket recovery. A live socket is never deleted. After an abrupt crash, lease recovery may take approximately 30 seconds.

## Interrupted topic creation

Topic creation is not idempotent. Before calling Telegram, the registry records an unresolved binding. If the call or subsequent registry write is interrupted, automatic creation for that binding is blocked to avoid duplicate topics. Recovery currently requires manual inspection with all Telegram connections stopped: identify whether Telegram created the topic, then restore the numeric topic ID for the hashed binding, or remove the unresolved entry only after confirming that no topic was created. Do not delete the whole registry; that loses existing task/topic links. There is no recovery UI yet.

## Verification and limitations

The core, webview and coordinator bundle are shared by VS Code and the JetBrains editions (PhpStorm, IntelliJ IDEA and applicable PyCharm targets). Platform-specific release packaging remains separate; this change does not alter IDE compatibility ranges or installed plugins.

Automated checks cover TypeScript, targeted settings acknowledgement/remount and manager races, queued approval invalidation/one-shot callbacks and acknowledgement failures, six-day rotation, incoming photo/document/caption routing, unauthorized and stale downloads, size/format/path/error limits, polling/stop independence, bounded ordering, task feedback and model image blocks, and existing task/provider/UI regressions. Real local Unix socket MCP tests cover authentication and the server's 32-request concurrency limit, including unresolved activation promises. Local attachment race tests verify fail-closed behavior on macOS; Linux-specific pinned-descriptor cases require Linux CI and are skipped on macOS. No real bot, IDE launch, Windows named-pipe session or packaged JetBrains runtime has been verified. English and Russian strings are present; other locales currently use the English fallback. Release archives, installation and publication are separate approval steps.
