# IVOL: совместная диагностика плагина и прокси — протокол v1

Статус: **предложение для согласования с серверным разработчиком**, 2026-09-09.
Это техническое задание, не описание уже работающего API. Сервер и плагин пока не изменены.

## 1. Задача и разделение работы

У пользователей VS Code короткая проверка модели завершается успешно, а обычная задача получает
`ECONNRESET`. При этом в прикладном мониторе прокси соответствующий запрос может отсутствовать.
Сам код ошибки не указывает, кто оборвал соединение и на каком этапе.

Нужен общий диагностический сеанс: пользователь нажимает кнопку в плагине, плагин выполняет
несколько контролируемых запросов, сервер сохраняет свои наблюдения, обе стороны сопоставляют
результаты по идентификаторам. Страница сервера показывает объединённый отчёт.

**Серверная сторона реализует:** API ниже, наблюдение на входном сетевом слое, хранение результатов
с проверкой владельца и страницу просмотра. Не требуется менять модель или предоставлять доступ
к серверу разработчику плагина.

**Со стороны плагина после согласования реализуем:** кнопку, последовательный исполнитель
проверок в extension host, локальный отчёт, отправку разрешённых диагностических полей,
отмену и открытие серверной страницы в обычном браузере. Не запускаем проверки из браузерного
JavaScript: это другой клиент, не воспроизводящий сетевой путь расширения.

Первое внедрение проверяем в VS Code. Общую реализацию затем проверяем в поддерживаемых
JetBrains-адаптерах; успешный тест одной IDE не обозначает проверку остальных.

## 2. Когда показывать кнопку

- Отдельная кнопка **«Диагностика IVOL»** рядом с существующей общей проверкой провайдера.
- Только для OpenAI Compatible и адреса с точным HTTPS-origin `https://prox.ivol.pro`.
  Стандартный порт 443 допустим. Поддомены, похожие имена, HTTP, другие порты и URL с userinfo
  не допускаются. Нельзя проверять адрес через `includes("ivol.pro")`.
- Базовый путь профиля, например `/v1`, не меняет адрес диагностического API: он находится от
  корня этого же origin. Адрес обычной генерации сохраняется без изменений.
- `pr.ivol.pro` и другие возможные алиасы **не включать автоматически**: их список отдельно
  подтверждает владелец. Кнопка у остальных провайдеров не появляется, обычная проверка остаётся.
- Диагностика использует **сохранённый активный профиль** текущего окна. При несохранённых
  изменениях попросить пользователя сохранить либо отменить их; не сохранять автоматически.
  Если в форме выбран неактивный профиль, сначала попросить явно активировать его; не тестировать
  вместо него другой профиль, который сейчас активен.
  Смена профиля/режима во время проверки отменяет сеанс, результаты разных профилей не смешиваются.
- Перед запуском показать: «Синтетические сетевые проверки; файлы и история проекта не отправляются.
  На сервер будут переданы технические результаты». Никакого фонового запуска.

## 3. Адреса и авторизация

Предлагаемый API: `https://prox.ivol.pro/ivol-diagnostics/v1`.
Предлагаемая страница: `https://prox.ivol.pro/diagnostics/runs/{run_id}`.
Если эти пути заняты, серверная команда предлагает окончательные **до реализации клиента**.

Каждый запрос API авторизуется действующим ключом выбранного профиля, как обычный запрос к этому
провайдеру. Для стандартной настройки это `Authorization: Bearer <ключ профиля>`.
Ключ не передаётся в URL, JSON, имени файла, отчёте или событиях журнала. Если поддерживаются
дополнительные авторизационные заголовки, сервер должен подтвердить их контракт отдельно;
их значения также нельзя записывать в диагностику.

Запросы с ключом не перенаправляются: клиент запрещает redirects. Диагностический API не должен
отвечать редиректом на вход в кабинет. Возвращать HTTP 401/403 с безопасным JSON-кодом ошибки.
Не менять TLS/VPN/proxy-настройки ради успешного теста. Клиент использует действующую политику
профиля; если она не позволяет получить конфигурацию сервера, остаётся локальный отчёт.

`run_id` — случайный UUID, который клиент создаёт **до первого запроса**, а не секрет доступа.
`attempt_id` — новый UUID для каждой попытки. `case_id` — идентификатор известного сценария.

Заголовки запросов:

```text
X-IVOL-Diag-Version: 1
X-IVOL-Diag-Run-Id: <UUID>
X-IVOL-Diag-Attempt-Id: <UUID>
X-IVOL-Diag-Case-Id: <фиксированный case_id>
```

`Run-Id` и `Attempt-Id` обязательны для всех запросов API. Для служебных create/status/report/cancel
заголовок `Case-Id` **отсутствует**, они не считаются испытаниями. Для ping, probes и отдельной
реальной генерации `Case-Id` обязателен. Если ID также присутствует в URL/JSON, значения должны
совпадать с заголовками; иначе HTTP 400. Идентификатор служебного запроса не добавляется в
`server_attempts` как результат испытания.

Ответы API: `Cache-Control: no-store`, `X-IVOL-Diag-Run-Id` и фактический
`X-Request-Id`, если его создаёт обслуживающий компонент. Идентификаторы проверять по формату,
ограничивать по длине, не использовать как произвольный путь к файлу.

## 4. API сеанса

| Метод и путь относительно API          | Назначение                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------- |
| `POST /runs`                           | Создать/получить сеанс с клиентским `run_id`, согласовать доступные сценарии |
| `GET /runs/{run_id}/ping`              | Маленький ответ без тела запроса                                             |
| `POST /runs/{run_id}/probes/{case_id}` | Выполнить ровно одну синтетическую проверку                                  |
| `POST /runs/{run_id}/client-report`    | Сохранить разрешённые наблюдения клиента                                     |
| `GET /runs/{run_id}`                   | Получить серверные наблюдения и состояние отчёта; не запускает проверки      |
| `POST /runs/{run_id}/cancel`           | Отметить отмену и остановить ещё выполняющиеся синтетические сценарии        |

Все операции требуют авторизации и проверки владельца сеанса. Административный доступ к отчётам
пользователей предоставляется отдельно, обычный пользователь не читает чужие сеансы.

Пример тела `POST /runs` — значения условные, версия берётся из реально работающего плагина:

```json
{
	"protocol_version": 1,
	"run_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
	"suite": "quick",
	"client": {
		"extension_version": "5.16.239",
		"ide": "vscode",
		"ide_version": "1.136.2",
		"os": "win32",
		"arch": "x64",
		"node_version": "24.18.1"
	},
	"profile": {
		"source": "saved_active",
		"provider": "openai",
		"origin": "https://prox.ivol.pro",
		"api_route": "/chat/completions",
		"model_id": "gpt-6-astra",
		"streaming": true,
		"allow_insecure_tls": false
	}
}
```

`api_route` передавать только для известных стандартных путей `/chat/completions` или
`/v1/chat/completions`. Для нестандартного пути — `null`, не отправлять потенциально секретные
URL-параметры. Не передавать название профиля, проект, имя пользователя ОС или локальные пути.

Пример ответа создания: HTTP 201, при повторе того же `run_id` тем же владельцем — HTTP 200
с существующим сеансом, без повторного запуска:

```json
{
	"protocol_version": 1,
	"run_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
	"state": "ready",
	"capabilities": {
		"cases": ["ping", "post_1k", "post_64k", "post_256k", "post_task_shape", "sse_chunks"],
		"max_body_bytes": 1048576,
		"max_client_report_bytes": 32768,
		"max_run_seconds": 120
	},
	"observability": {
		"ingress_headers": "available",
		"ingress_body": "available",
		"application": "available",
		"tls_failures": "unavailable"
	},
	"expires_in_seconds": 86400
}
```

Источники наблюдений указывать честно: `available`, `unavailable` или `partial`. Не заявлять
поддержку события, если стек сервера технически его не предоставляет.

Клиент знает сценарии заранее. Сервер может отключить сценарий, понизить лимит и сообщить
возможности; неизвестные сценарии не исполняются. Серверные числа не могут увеличить жёсткие
ограничения клиента. При несовместимой версии — понятное «протокол не поддерживается».

### Состояние и завершение сеанса

- `state` на сервере: `ready`, `running`, `completed`, `cancelled`, `expired`.
- Create создаёт `ready`; первое испытание переводит его в `running`.
- `POST client-report` с `final: true` завершает активный сеанс: после проверки и сохранения
  отчёта состояние становится `completed`, ограничение «один активный сеанс» освобождается.
  Пробовать новые сценарии в завершённом сеансе нельзя.
- `POST cancel` переводит активный сеанс в `cancelled` и освобождает ограничение. Факт того,
  что ещё работающий поток действительно остановлен, регистрируется отдельным событием.
- По истечении серверного `max_run_seconds` от момента create активный сеанс становится `expired`:
  это освобождает слот, даже если клиент не смог отправить завершение/отмену.
- Поздний финальный клиентский отчёт можно сохранить в `cancelled`/`expired`, не возобновляя сеанс
  и не переписывая его терминальное состояние. Повтор того же финального отчёта идемпотентен;
  попытка заменить его другим финальным отчётом — HTTP 409.
- Отдельный `outcome`: `passed`, `partial`, `failed`, `cancelled`, либо `null` до получения итога.
  `completed` не означает успех: в завершённом сеансе могут быть ошибки.
- Quick содержит 6 испытаний, extended — те же 6 плюс 3 задержки. Реальная генерация, если
  реализована, создаёт **новый** сеанс `suite: "generation"`, а не дополняет завершённый.
  В нём до 2 испытаний, общий срок — 150 секунд; они перечислены в разделе 8.
- Срок хранения отчёта (`expires_in_seconds`, 24 часа) отличается от срока выполнения сеанса.

Пример безопасной ошибки (HTTP-статус соответствует фактической ошибке):

```json
{
	"protocol_version": 1,
	"run_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
	"attempt_id": "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb",
	"error": { "code": "BODY_TOO_LARGE" }
}
```

Если идентификатор отсутствует или не прошёл проверку, возвращать `null`, не отражать произвольный
ввод. Минимальные коды: `INVALID_REQUEST`, `UNSUPPORTED_PROTOCOL`, `UNKNOWN_CASE`,
`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `RUN_ACTIVE`, `RUN_CLOSED`, `REPORT_CONFLICT`,
`DUPLICATE_ATTEMPT`, `BODY_TOO_LARGE`, `RATE_LIMITED`, `INTERNAL_ERROR`. Сырой текст исключений
и HTML-страницы ошибок не включать в JSON. Ошибка входного слоя может быть не-JSON: клиент
должен это выдерживать, сохраняя статус и этап без копирования тела.

## 5. Синтетические проверки — без вызова LLM

Выполнять последовательно, без нагрузочного тестирования. Использовать тот же механизм
HTTP/TLS/proxy, которым пользуется обычная генерация расширения.

| `case_id`         | Запрос и ожидаемый результат                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `ping`            | GET; маленький JSON с идентификаторами и серверным временем                                                                              |
| `post_1k`         | POST JSON ровно 1 024 байта; сервер подтверждает размер и SHA-256                                                                        |
| `post_64k`        | То же, ровно 65 536 байт                                                                                                                 |
| `post_256k`       | То же, ровно 262 144 байта                                                                                                               |
| `post_task_shape` | POST с синтетическими `model`, `messages`, `tools`, `stream`; подтверждение получения, без выполнения инструментов и без отправки модели |
| `sse_chunks`      | POST; HTTP 200 и 8 SSE-событий с порядковыми номерами через каждые 2 секунды, затем `done`                                               |

Тело size-тестов: JSON-объект с `protocol_version`, `run_id`, `attempt_id`, `case_id`,
`padding`. Клиент заполняет `padding` безопасной повторяемой ASCII-строкой так, чтобы
**всё сериализованное UTF-8-тело**, а не только строка, имело требуемый размер. Без сжатия запроса.
SHA-256 считается по исходным байтам HTTP-тела до JSON-парсинга. Сервер не возвращает тело.

`post_task_shape`: только заранее подготовленный фиктивный системный текст, пользовательский
текст «diagnostic», определение одного фиктивного инструмента и синтетическое наполнение до
64 КиБ. Ни системные инструкции реальной задачи, ни файлы проекта не используются. Ожидаемый
ответ — такое же подтверждение размера/хеша. Это проверка передачи структуры, **не доказательство
поддержки инструментов выбранной моделью**.

Успешный JSON-ответ POST-проверки:

```json
{
	"protocol_version": 1,
	"run_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
	"attempt_id": "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb",
	"case_id": "post_64k",
	"outcome": "ok",
	"received_body_bytes": 65536,
	"received_body_sha256": "<64 lowercase hex characters>",
	"server_request_id": "<opaque bounded identifier>",
	"server_time_utc": "<ISO 8601 UTC>"
}
```

SSE: `Content-Type: text/event-stream`, UTF-8. Каждое событие заканчивается пустой строкой;
клиент не предполагает, что сетевой chunk совпадает с SSE-событием. Пример:

```text
event: tick
data: {"protocol_version":1,"run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","attempt_id":"bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb","case_id":"sse_chunks","seq":1,"server_time_utc":"<ISO 8601 UTC>"}

event: done
data: {"protocol_version":1,"run_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","attempt_id":"bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb","case_id":"sse_chunks","events_sent":8}

```

Для потокового маршрута обеспечить реальную отправку заголовков/событий без накопления
буфером или компрессором. Зафиксировать, какие настройки отличаются от production-маршрута:
нельзя выдать успех специально облегчённого маршрута за доказательство исправности обычного.

Расширенный режим, только отдельным действием пользователя, добавляет фиксированные сценарии:

- `delay_headers`: ждать 15 секунд **до отправки HTTP-заголовков**, затем вернуть JSON.
- `delay_first_event`: сразу отправить и сбросить HTTP-заголовки, через 15 секунд — первое SSE-событие.
- `sse_idle`: отправить первое событие сразу, 75 секунд ничего не отправлять, затем `done`.
  Heartbeat в этой паузе запрещён: он замаскирует проверяемый idle-timeout.

`delay_headers` возвращает JSON-подтверждение по форме echo-ответа. `delay_first_event` отправляет
один `tick` с `seq: 1` и затем `done` с `events_sent: 1`; `sse_idle` также содержит один `tick`
и `done`. В `sse_chunks` первый `tick` отправляется сразу, остальные — через интервалы по 2 секунды;
после восьмого идут `done` и завершение HTTP-ответа. Во всех потоках flush заголовков предшествует
ожиданию событий, кроме отдельного сценария задержки заголовков.

Клиентские пределы: 10 секунд на ping/echo, 25 секунд на `sse_chunks` и короткие задержки,
90 секунд на `sse_idle`; весь quick-сеанс — максимум 120 секунд, extended — 300 секунд.
При исчерпании общего бюджета оставшиеся шаги помечаются `not_run`, а не `failed`.

## 6. Что сервер должен наблюдать

Для каждой попытки нужны события **от реально наблюдавшего компонента**, по мере возникновения:

1. Входной reverse proxy/LB: `headers_received`, `body_read_started`, `body_read_completed`
   или ошибка/обрыв чтения тела.
2. Приложение: `app_entered`, `body_validated`.
3. Ответ: `response_headers_sent`, `first_event_sent`, `response_completed` или `connection_closed`.

Поля события: `run_id`, `attempt_id`, `case_id`, `source` (`ingress`/`application`), `stage`,
`at_utc`, фактически известные счётчики байтов и безопасный код ошибки. Отсутствующее значение
оставлять `null`, не придумывать HTTP 200 или нулевую длительность.

Если Nginx/FastCGI или другой слой буферизует тело до передачи приложению, **одного PHP-журнала
недостаточно**. Нужен предусмотренный стеком журнал/трассировка входного слоя. Обычная запись
access-log только при завершении запроса не равна событию его начала.

При сбое DNS/TCP/TLS до расшифровки HTTP-заголовков сервер ещё не видит `run_id`.
Такие события можно дополнительно искать по времени и сетевым признакам в защищённых
журналах ingress, но это неточная корреляция. Показывать `correlation: "heuristic"` либо
`"unavailable"`, а не выдавать её за совпадение по UUID. IP-адреса не включать в пользовательский
отчёт; они могут оставаться в обычных защищённых журналах сервера.

**`not_observed` означает «не найдено в доступных источниках», а не «не дошло до сервера».**
Отправка/flush сервером события также не доказывает его получение клиентом.

## 7. Наблюдения клиента и объединённый отчёт

Клиент сохраняет последовательность: `prepared`, `fetch_started`, `http_headers_received`,
`first_event_received`, `response_completed` либо `error`/`timeout`/`cancelled`.
`fetch_started` означает вызов сетевого механизма, **не подтверждение отправки всех байтов**.

Передавать в `POST /runs/{run_id}/client-report` только ограниченный JSON:

```json
{
	"protocol_version": 1,
	"run_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
	"final": true,
	"outcome": "partial",
	"attempts": [
		{
			"attempt_id": "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb",
			"case_id": "post_64k",
			"started_at_utc": "<ISO 8601 UTC>",
			"elapsed_ms": 4200,
			"last_observed_phase": "fetch_started",
			"outcome": "error",
			"error_code": "ECONNRESET",
			"http_status": null,
			"server_request_id": null,
			"prepared_body_bytes": 65536,
			"received_body_bytes": 0
		}
	]
}
```

Ответ на принятый `client-report` — HTTP 200, JSON с `protocol_version`, `run_id`,
`accepted: true`, текущим серверным `state` и `stored_at_utc`. Сохранить отчёт **до** подтверждения.
Для `cancel` — HTTP 200 с `protocol_version`, `run_id`, `state` и `cancel_requested: true`;
если сеанс уже терминальный, сохранить это состояние. Для `ping` — HTTP 200 с `protocol_version`,
`run_id`, `attempt_id`, `case_id: "ping"`, `outcome: "ok"`, `server_request_id` и `server_time_utc`.

Длительности клиент измеряет монотонными часами. UTC нужен для поиска, но часы клиента и сервера
могут расходиться. Время и профиль фиксируются при попытке, не при открытии окна ошибки.

Локально также проверять совпадение идентификаторов, размера/хеша echo, количество и порядок SSE,
наличие `done` и нормального конца ответа. Лимит ответа — 64 КиБ, отчёта клиента — 32 КиБ.
Коды ошибок — allowlist; неизвестные — `UNKNOWN`, без сырых исключений и stack trace.

`GET /runs/{run_id}` возвращает `protocol_version`, `run_id`, `state`, `observability`,
`server_attempts`, `client_report` (либо `null`) и срок хранения. `server_attempts` содержит
по одному объекту на `attempt_id`: `case_id`, `outcome`, `events` с полями из раздела 6.
Серверные и клиентские факты не смешивать и не заменять друг другом.

Страница показывает таблицу «сценарий → что увидел клиент → что увидел ingress → приложение →
последний подтверждённый этап». `outcome` и серверное `state` различаются, как описано в разделе 4.
Успешный результат именуется **«синтетический транспорт проверен»**, не «все задачи исправны».

Если создание сеанса или отправка отчёта не удались, локальные результаты и UUID остаются
доступны для копирования. Не показывать «отчёт отправлен», пока сервер не подтвердил приём.
Тесты не повторять автоматически. Повтор пользователем — новая попытка с новым `attempt_id`.
Повтор передачи того же отчёта идемпотентен; повтор create не запускает тесты.

## 8. Проверка настоящего API — отдельно

Специальный URL может работать, когда `/chat/completions` не работает из-за отличающихся правил
маршрутизации, защиты или лимитов. Поэтому синтетические проверки не заменяют проверку
фактического API-маршрута.

После базового сеанса можно предложить отдельное **«Проверить генерацию — возможна тарификация»**:
короткий фиксированный текст, выбранная модель и тот же профиль, без проекта/истории/веб-поиска.
Создать новый сеанс `suite: "generation"` и показать его отдельный код. Не расширять программу
сеанса без согласия. Использовать `case_id: "generation_text"` и `"generation_tool_schema"`.
Передавать идентификаторы этого нового сеанса на обычный Chat Completions endpoint и
записывать их на ingress и в обработчике прокси. Диагностические заголовки не пересылать upstream.
Обычное поведение endpoint не меняется, наличие заголовка само по себе не означает dry-run.

Предлагаемые пределы этой отдельной функции: максимум две явно обозначенные попытки
(без tools / с одним фиктивным function tool), до 60 секунд и до 4096 выходных токенов на попытку,
без автоматических повторов. Клиент применяет лимит через поддерживаемые параметры своего
адаптера; неподдерживаемая комбинация помечается `unsupported`, а не тихо меняет модель.
Никакой инструмент из ответа не исполняется. Исчерпание бюджета рассуждений без текста
показывается отдельно от сетевого обрыва. Отмена не гарантирует остановку вычислений upstream.

Реальная генерация — дополнительный этап, не обязательный для первой реализации серверного API.

## 9. Безопасность, нагрузка и страница

- Сервер возвращает только данные фиксированного протокола: никаких JavaScript, shell-команд,
  произвольных URL, шаблонов запросов или указаний отключить TLS. Клиент не загружает исполняемый код.
- Серверная страница открывается обычным браузером; у неё нет привилегированного моста к IDE.
  Просмотр требует входа в соответствующий аккаунт или административного доступа. UUID не даёт
  право чтения. Если у пользователя нет доступа к кабинету, он передаёт код проверки поддержке.
- Не хранить ключи, cookies, значения заголовков, исходные тела, ответы модели, код проекта,
  историю задач, локальные пути и сырые ошибки. Не включать debug-логирование полных запросов.
- Валидация JSON, разрешённых полей, сценариев, размеров, UUID и принадлежности владельцу обязательна.
  Неизвестный сценарий — HTTP 400 с машинным кодом, неизвестная чужая сессия — безопасный 404.
- Тело запроса ограничить 1 МиБ; при превышении — HTTP 413, без накопления произвольного объёма в памяти.
  Сервер не должен для этих маршрутов ослаблять обычную сетевую защиту, маскируя проблему.
- Один активный сеанс на пользователя; предложенный лимит — 3 запуска за 10 минут, до 10 попыток
  испытаний на сеанс (служебные create/status/report/cancel в эти 10 не входят и имеют отдельный
  rate-limit). Quick — 6, extended — 9, отдельный generation — 2. Повтор одного `attempt_id`
  не выполняет испытание снова: HTTP 409 `DUPLICATE_ATTEMPT`; сохранённые наблюдения доступны через GET.
  Дополнительный IP-limit для неавторизованных запросов; HTTP 429 и `Retry-After`.
- `cancel` идемпотентен: запрещает новые шаги, останавливает серверные таймеры/потоки, когда возможно.
  В отчёте различать «отмена запрошена» и «остановка подтверждена». Сохранить уже собранные результаты.
- Предложенный срок хранения отчёта — 24 часа. Показывать срок пользователю. Диагностика не должна
  создавать бессрочное хранилище пользовательской активности.
- Обновлять на сервере страницу, пояснения и выбор из уже известных сценариев можно без новой
  версии плагина. Новый сетевой механизм или новый тип сценария потребует обновления клиента.

## 10. Что серверная команда возвращает перед интеграцией

1. Подтверждённые origin, пути API/страницы, способ авторизации и ограничения.
2. Готовые примеры create, echo, SSE, report и ошибок 401/403/413/429.
3. Перечень реально доступных событий ingress/TLS/application и всех отличий от production-маршрута.
4. Способ доступа пользователя и администратора к странице; политику хранения.
5. Доступность тестового развёртывания. Производственный пользовательский ключ в ТЗ не включать.

После этого реализуем клиент по согласованному контракту и проверяем: обычный успех, сбой до
заголовков, обрыв посередине SSE, неполное тело, отмену, отсутствие журнала ingress, неверный ключ,
попытку доступа к чужому UUID, превышение лимита и несовпадающую версию протокола.
Не считать соединение реального пользователя исправленным только по результатам локальных тестов.
